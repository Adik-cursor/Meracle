# План доведения Meracle до SaaS

Этот документ фиксирует проверенные разрывы между текущим приложением и рабочей многопользовательской SaaS-платформой. Пункты идут по зависимости: нижние слои нужно закрывать до запуска на реальных организациях.

## 1. Серверная база и авторизация — блокирующий пробел

### Текущее состояние

- `src/app/context/PersistenceContext.tsx` создаёт браузерное хранилище через `createBrowserPersistence()`.
- `src/core/repositories/browser/create-browser-persistence.ts` загружает и сохраняет состояние приложения в `localStorage` под одним ключом `crm-platform.persistence`.
- `src/app/routes/pages/LoginPage.tsx` показывает список пользователей и выполняет вход по `userId`, без пароля.
- `src/core/services/auth.ts` создаёт сессию в локальном репозитории. Это не серверная сессия и не удостоверение пользователя.
- `docs/database-schema.md` описывает будущую схему PostgreSQL и прямо говорит, что подключения к базе, API и сервера пока нет.
- В `package.json` нет backend-команд или зависимостей API/БД. В текущем окружении не обнаружены PostgreSQL, строка подключения или переменные API.

### Последствие

Данные не общие для сотрудников и устройств, не защищены серверной границей организации и не могут служить надёжной рабочей базой SaaS. Проверки доступа в клиентском коде не заменяют авторизацию и tenant isolation на сервере.

### Целевое состояние

1. API и PostgreSQL как единственный источник истины для бизнес-данных.
2. Вход по email и паролю; хэш пароля и серверная сессия в `HttpOnly`, `Secure`, `SameSite` cookie.
3. `organizationId`, роль и разрешения вычисляются сервером по сессии; клиент не может выбрать пользователя или tenant самостоятельно.
4. Все чтения и записи проверяют организацию и разрешение на сервере; межорганизационные связи защищены ограничениями базы.
5. Версионированные миграции, резервное копирование и проверка восстановления до пилотного запуска.

### Этапы

- [ ] Зафиксировать серверный контракт, ошибки API и переходный режим для существующих данных.
- [ ] Поднять PostgreSQL для разработки, применить первую миграцию и подключить сервер.
- [ ] Реализовать приглашение/создание аккаунта, пароль, вход, выход, восстановление доступа и серверные сессии.
- [ ] Перенести tenant-контекст и проверки доступа на сервер.
- [ ] Перевести модули с браузерного persistence на API по одному, начиная с аккаунтов и организации, затем продажи/склад/финансы.
- [ ] Добавить перенос старых данных из браузера с предварительным экспортом и подтверждением целевой организации.
- [ ] Проверить изоляцию нескольких организаций, конкурентные продажи и восстановление резервной копии.

## 2. Необходимые после backend этапы

- [ ] Проверить каждое разрешение на сервере, особенно склад, деньги, возвраты, кадровые и детские данные. `docs/rbac.md` указывает, что складской RBAC не подключён к runtime, а `docs/financial-rbac.md` — что финансовые разрешения не подключены к существующим sales/payment services.
- [ ] Подключить фискализацию и обработку ошибок/повторных отправок; интерфейс сейчас явно сообщает, что фискальный чек недоступен.
- [ ] Настроить эксплуатацию: секреты, HTTPS, журналирование, мониторинг, миграции, резервные копии, лимиты хранения файлов и процедуру восстановления.
- [ ] Пройти end-to-end сценарии по каждому бизнес-шаблону и роли на серверной базе.

## Текущие проверки

- `npm run lint` — успешно на текущем исходном состоянии.
- `npm run build` — успешно; остаются предупреждения о крупных клиентских чанках и неэффективных динамических импортах PDF-модулей.

## Ближайший отдельный пробел

Начать с серверного контура авторизации и PostgreSQL, а не маскировать отсутствие backend настройкой интерфейса. Для локальной разработки можно использовать PostgreSQL по схеме из `docs/database-schema.md`; перед подключением существующих бизнес-данных нужен отдельный безопасный план миграции из `localStorage`.
